# ADR-006: Comparative bootstrap forecast policy

Status: Proposed for review under #17; accepted when this PR merges. Implements approved Q03: cash earns zero return. #20 owns transport/schema implementation, #21 independent fixtures and #48 the forecast engine. This document does not implement a production forecast.

## Immutable inputs and supported comparison

Method `multivariate_block_bootstrap_v1` compares current and proposed allocations using the same historical shocks. Inputs are pinned snapshot/manifest and calendar versions, decision cutoff/as-of session, coherent current valuation and portfolio revision, strategy/config hash, current/proposed complete asset and cash weights, estimated upfront costs, method parameters, engine build and seed. Missing inputs cannot be inferred from a later refresh. Weights are long-only, finite, nonnegative and sum to one including cash within 1e-8; reject invalid policies rather than normalize an unintended allocation. Initial NAV must be a positive finite decimal amount; valuation timestamps and quality must be known.

Model defaults are 90 calendar days, 252 completed daily return vectors, five-session blocks and 5,000 paths. V1 fixes these methodological defaults; a later configurable method requires a versioned contract. The seed is an integer in [0, 2^64−1], default42. Resource admission follows ADR-005, including its 16-asset union ceiling. A larger valid portfolio may therefore have an unavailable comparison; never drop its positions or silently lower path count. This is a scenario model, not a forecast of individual execution prices or an authorization to trade.

## Common history and horizon

Form the sorted union of assets with positive weight in either case; zero-weight assets do not require history. Use the **same last 252 scheduled exchange-session returns ending at T** for every asset, requiring 253 positive finite adjusted closes T−252 through T. The interval is determined from the pinned calendar, not from each asset's surviving rows. A missing bar, invalid adjustment basis, nonfinite return, unavailable publication evidence or absent asset makes the whole comparison unavailable with the precise reason. Do not forward-fill, stitch an older window, use different histories per portfolio, or drop difficult holdings. Each input observation must be available by the original decision cutoff under ADR-002; future data in the snapshot is excluded. Use simple return `P[t]/P[t−1]−1`, with adjusted-close basis declared; dividends are not added again.

Add 90 **calendar dates** to the decision timestamp in `America/New_York`, retaining its local wall-clock time, then convert the resulting endpoint to UTC with the pinned timezone rules. Count calendar sessions whose closes are strictly after the cutoff and at or before that endpoint. Record the start/end timestamps and explicit future session dates used. DST changes may change elapsed UTC hours. Do not substitute 90 trading days or a fixed 63-session approximation. Missing calendar coverage yields `CALENDAR_UNAVAILABLE`; an empty resulting session set yields `ZERO_SESSION_HORIZON`, not a fabricated interval. The fixed 90-day default normally contains many sessions; the zero-session check is still required for invalid/truncated calendars and future method extensions.

If both cases contain only cash, no asset history or RNG draws are required: all paths have zero gross return under Q03, with known upfront costs still applied. Calendar, valuation and cutoff validation still apply. If either case has an asset, the common-history requirements apply to the complete union, even when the other case is all cash.

## Sampling and numerical reproducibility

Use `numpy.random.Generator(numpy.random.PCG64(seed))`; the initial locked numerical implementation is NumPy2.5.4. Record the NumPy version, bit-generator name, initial state and sampling algorithm version. [NumPy documents PCG64's seeded integer-stream guarantee](https://numpy.org/doc/stable/reference/random/bit_generators/pcg64.html); this does not imply every floating-point computation or distribution API is stable across versions/platforms.

For H future sessions, draw a C-order integer array of shape `(5000, ceil(H/5))` using `Generator.integers(low=0, high=248, dtype=int64, endpoint=False)`. Each entry is a uniformly selected **non-circular** starting row from 0 through247 in the 252-row history. Append its five consecutive **whole cross-asset vectors**; concatenate blocks in draw order and truncate only the final tail to H. Blocks may overlap and be selected repeatedly. No per-asset random draws, wrapping beyond history, or separate RNG stream per comparison. Persist the sampled-index artifact hash and enough versioned metadata to reproduce it. A test seam may accept a fixed index stream but must not change production sampling semantics.

Canonical asset ordering is ascending immutable asset_id. Persist float64 input-array digest with declared shape, column order, little-endian encoding and row dates; canonicalize to that encoding before hashing. Array hashes establish exact bytes, while semantic provenance is also retained. Same pinned software/platform and inputs must reproduce indices and output arrays. Cross-platform small numerical differences must be disclosed and tested to documented tolerances rather than mislabeled bitwise identity.

The forecast fingerprint is SHA-256 of the canonical JSON object containing all immutable inputs above, normalized weights/NAV/costs, method parameters, seed/RNG/NumPy/engine versions, array/index hashes and horizon endpoints/session list. Use ADR-003's canonical serialization rules, extended to ordered arrays without reordering them; field `fingerprint_schema_version=1` is mandatory. Decimal financial values are normalized strings; finite statistical metadata retains number type. Exclude generated forecast UUID and creation wall-clock time. Hash the effective recorded inputs, not mutable database aliases. Changing cost, ordering, cutoff, data, model or seed must invalidate reuse.

## Valuation, costs and constant weights

For case c and path p, define each step's return as `r[c,p,t] = sum_i(w[c,i] * sampled_return[p,t,i])`; the cash term is exactly0. Weights are constant at every step. This is a frictionless constant-mix approximation: it implicitly maintains weights, rather than modeling buy-and-hold drift, discrete rebalances, taxes or subsequent order costs. Disclose this explicitly; no scenario writes holdings or orders.

Let original current NAV be V. Current/hold case starts at V with zero upfront cost. Proposed case starts at V−C, where C is the nonnegative estimated slippage plus commission cost of its previewed change, computed using the pinned as-of prices and ADR-001 policy. Trade notional itself is exchanged value, not a cost. Do not include future opening quotes, double-charge costs already deducted from the supplied NAV, or add costs again on every scenario step. Missing reliable cost/valuation inputs yield an unavailable comparison. Reject C>=V for this supported model; it cannot leave a positive starting value. Estimated cost is not a promise of actual next-open execution.

Ending value is `(V−C_c) * product_t(1+r[c,p,t])`. Report return relative to the **same original V**: ending_value/V−1, so upfront costs count against the proposed case. No ledger cent rounding occurs between steps. Output money values are decimal strings rounded once to cents with ROUND_HALF_EVEN at presentation; statistical fields remain finite float64 values. Scenario arithmetic is not the Decimal cash ledger. Preserve unrounded paths for reproducibility and quantile checks.

Compute P10/P50/P90 using sorted returns and linear interpolation: index `(N−1)*q`, interpolate between floor and ceiling indices. Probability of loss is count(return<0)/N; exactly zero is not a loss. Median ending value is the same interpolation over ending values, then rounded for display. The comparison's median-return delta is proposed median minus current median; do not label it probability of outperformance or the median of paired differences. Identical weights with zero cost must use identical sampled shocks and produce identical arrays and metrics.

## Available and unavailable output

Extend the API forecast envelope with decision cutoff, source mode, snapshot/calendar references, horizon endpoint/session count, current/proposed weight and cost metadata, fingerprint, RNG/numerical versions, array/index artifact references, `cash_return_fraction=0`, and limitations `SCENARIO_NOT_CALIBRATED_PREDICTION`, `ZERO_CASH_YIELD`, `CONSTANT_WEIGHT_APPROXIMATION`, `ESTIMATED_UPFRONT_COST`. Include current/proposed distributions and the defined median delta only when the comparison is available.

For unavailable output, set `status="unavailable"`, `unavailable_reason` to an explicit code, and `proposed`, `hold_unchanged` and comparison outcomes to null. Preserve known input/provenance fields; unknown counts/endpoints are null, not invented. Reason codes include `INSUFFICIENT_ALIGNED_HISTORY`, `ASSET_UNAVAILABLE`, `UNSAFE_PRICE_BASIS`, `EVIDENCE_AFTER_CUTOFF`, `VALUATION_UNAVAILABLE`, `COST_UNAVAILABLE`, `CALENDAR_UNAVAILABLE`, `ZERO_SESSION_HORIZON`, `WORKLOAD_LIMIT` and `NONFINITE_RESULT`. Distinguish malformed requests (422 validation/admission error) from a valid job whose available data cannot support a forecast. An unavailable forecast is an explicit model result, not a successful numerical prediction or a concealed worker crash.

User-facing text must say scenario median/range, identify synthetic fixtures when used, and disclose zero cash yield and the constant-weight/cost assumptions. Never describe percentile bands as calibrated confidence, guaranteed outcomes, or an expected return established by this method. No fabricated zero outcome substitutes for unavailable data. Journal/counterfactual work inherits Q03 and original chronology (#57); this ADR does not redefine its later execution/outcome policy.

## Independent FIX-08 / FIX-02 oracles

1. Synthetic three-row vector history `[(0.10,−0.10),(0.20,−0.20),(0.30,−0.30)]`, test block length2, chosen starts `[1,0]`, horizon3 gives rows `[1,2,0]` and paired vectors `[(.20,−.20),(.30,−.30),(.10,−.10)]`. This deliberately small operator test is not a valid production252-row request. Two 50/50 portfolios have exactly zero step returns and identical terminal arrays. Sampling assets independently would fail the pairing assertion.
2. Sorted five-path returns `[−.20,−.10,0,.10,.20]` give P10=−.16, P50=0, P90=.16 and loss probability2/5. On V=1000 and zero cost, median ending value=1000.00. These are authored arithmetic fixtures, not market results.
3. All-cash current NAV1000, proposed all-cash with an explicitly supplied synthetic liquidation-cost estimate10: current ending1000.00/return0/loss0; proposed ending990.00/return−.01/loss1 on every path. This tests cost arithmetic, not a claim that an unchanged cash-only portfolio should pay a fee. Identical cash allocations with cost0 give identical paths.
4. Synthetic calendar input cutoff `2030-01-01T21:00:00Z` (16:00 New York), endpoint 90 local calendar days later `2030-04-01T20:00:00Z`. A deliberately abbreviated test schedule with future closes Jan2/Jan3/Apr1 before-or-at the endpoint counts3; Apr2 is excluded. This tests mapping only, not a complete real exchange schedule. An empty fixture schedule produces unavailable, never 90 sessions.
5. A common asset missing one close inside the required253-close window makes both outcome objects null. A bar available one second after cutoff is excluded even when downloaded into the pinned snapshot. Never replace it with an older row or an eventual corrected value.

Integer sampling indices, field presence and null/reason outcomes require exact equality. Small hand-derived return/quantile oracles use absolute tolerance1e-12; full float64 paths use absolute/relative1e-10 across supported platforms, with cent outputs exact after prescribed rounding. Golden expected arrays/quantiles must be independently constructed, not generated by the production function. #21 records fingerprints/index streams and #48 verifies the full engine.
